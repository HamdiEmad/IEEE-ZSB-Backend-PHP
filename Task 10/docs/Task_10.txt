(2). PHP Autoloading and Extractions
    - If the user tries to reach one of the project files in his browser, he will access if easily due to a big security concern that we haven't noticed earlier and should be handled.
    - The solution is to create a directory named public inside the project folder and move index.php to it and reinitialize the server again within public folder using the command 'php -S localhost:3000 -t public', now the public folder will be the parent folder to the server.
    - You will face several errors due to 'require' in the index folder and you can fix this by easily adding a variable named BASE_PATH and a helper function in finctions.php to help you not rewrite the whole path at avery require.

(4). Handle multiple request methods
    - To add a button in the note page to delete a specific note, a block of code is added in the views/notes/show.view.php file:
        - <form class="mt-6" method="post">
                <input type="hidden" name="id" value="<?= $note['id'] ?>">
                <button class="text-sm text-red-500">Delete</button>
            </form>
    - Notice that the method is POST request due to several reasons:
        - if it's like '<a href="/delete?id=5">Delete</a>' which considered a GET request, it is not safe for different actions which could be destructive.
        - POST is used when creating, updating or deleting the data which changes the server state.
    
(5). Build a better router
    - The old router is refactored to become cleaner, more scalable, and closer to real MVC architecture principles.
    - The old one faces many problems:
        - Routes were handled in a simple array or switch-like structure.
        - Controllers and logic were mixed or manually included.
        - Hard to scale when the project grows.
    - The new router class is created to acheive:
        - Move toward "One Request → One Controller" design.
        - Each URL should map to a single controller file/class.
        - Router only decides WHICH controller to run, not HOW it runs.

(7). First service container
    - When having many classes and many object of those classes which called instances and manually creating these instances, It becomes messy and repeitive so we have to figure a solution that solve this issue.
    - A valid solution is a service container acts as a 'box' where you describe how to build your objects instead of creating a new instance every time, you "resolve" it from the container.
    - So, I created a class named Container and 2 functions:
        - bind($key, $resolver): to bind a key (like a class name) to a function that returns an instance from that class.
        - resolve($key): It is usually used to get the object whenever you need it using the key.
    - A class named App was created to make the container easily accessible throughout the project. It's a static class acts as a wrapper for the container allowing you to call the App::resolve('Core\Database') from anywhere in your code.

(8). Implementation of PATCH Requests
    - Noticing that we have create and delete controllers but what if the user want to update a specific note ? There should be an Edit controller to handle this request.
    - First, I added the PATCH route to handle the submission of the edit form:
        - $router->get('/note/edit', 'controllers/notes/edit.php');
    - Then, I Edited the HTML from and add a hidden input named '_method' with the value 'PATCH' to deal with PATCH request because the HTML forms only support GET and POST.
    - And updated the database using 'UPDATE' SQL command and prevented SQL injection.
    - For sure after form validation, A user must be authorized to edit a specific note so an authorization function is used in the edit controller:
        - authorize($note['transaction_id'] === $currentTransactionId);

(9). PHP sessions

    - To start a new session, use a PHP function named session_start() that allows the server to regonize the user by storing a unique session ID in a cookie on the user's browser.
    - The superglobal '$_SESSION' is used to persist data across multiple page loads.

(11). Introduction to Middleware
    - A Middleware is defined as a layer of logic that runs after a request is received but before the controller handles it.
    - A logged-in user shouldn't be authorized to access register page and the guest user should stick to the registration page and doesn't access the other pages untill registration process completed and the user credentials are inserted into the database.
    - A class named Middleware is implemented to solve this issue containing a MAP array to map each type of users ('Authenticated', 'Guest', .....) to its own class to apply the logic of Middleware:
        - public const MAP = [
            'guest' => Guest::class,
            'auth' => Auth::class,
          ];

(12). Manage Passwords
    - A password should not ever never saved at it is in the database, It should be hashed first.
    - A PHP function called password_hash() is used to hash the password by adding some random data to the original password before hashing it to protect against attacks.
    - This method taked 2 parameters in most cases but originally, it takes 3:
        - $password: which is meant to be saved in the database after hashing process.
        - $algo: It is the algorithms of the hashing process (BCrypt, Argon2, ....)
